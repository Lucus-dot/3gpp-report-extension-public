# 踩坑清单（全部为真实发生过的错，按危害排序）

> 用法：写之前读一遍；`skillctl check` 报错时对照查。每条都给"症状 / 根因 / 处置"。

## P1　把相邻两个 Agreement 并成一条（计数少 1）
- **症状**：文中写"11 条 Agreement"，实际主席报告是 12 块。
- **根因**：两个 `Agreement:` 块在语义上属于同一议题（例："RO-Pair 的定义"与"两 RO 的时域关系"），写的时候顺手合并成一个小节。
- **处置**：以字符串 `Agreement:` / `Working assumption` 为**切分锚**逐块数，不按语义数。同一议题可以有两个 Ag，标题里用 `Ag④ / Ag⑤` 区分即可。
- **校验**：`skillctl check` 会校验 `AgN` 编号 1..N 连续；阶段 S2 的 gate 要求"计数 = 切分块数，误差 0"。

## P2　沿用上一场的计数
- **症状**：写"40 篇公司贡献"，逐条数是 41。
- **根因**：上一场的数字留在记忆/模板里。
- **处置**：**每场重新从主席报告的 tdoc 列表逐条计数**，并把花名册贴进文档（既是证据，也是下一场的基线）。
- **校验**：`skillctl check` 会比对「正文声明篇数」与「花名册实际条目数」（按表头里 TDoc 那几列逐格数），
  对不上直接 ERROR 并给出行号。

## P3　把 FL Summary #1 当成 tdoc 清单
- **症状**：文中写"清单见 R1-2607xxx"，实际那个号是 FL Summary #1。
- **根因**：FL 编号与会务清单编号相邻，且 tdoc 清单本身常常没有独立编号（就是主席报告里的列表）。
- **处置**：逐个核对 FL 的**标题**（`FL Summary #n: …`），不靠编号推。找不到独立清单时，直接说"清单见主席报告 tdoc 列表"。

## P4　把 FL 的 "Agree" 写成落槌
- **症状**：文中出现"已同意支持 X"，主席报告里没有该 Agreement。
- **根因**：FL Summary 是 Moderator 的对齐稿，措辞很像结论（`Agree to support` / `Proposal 1-2-2-v0`）。
- **处置**：一律降级为"仅 FL 级 Agree，未进主席报告"，并在总映射表里记为**停滞**而非已定。
- **校验**：每条 `【原文】` 必须能在 `_eom_*_verbatim.txt` 里 grep 到；grep 不到就是 P4。

## P5　`SCS×2^k`（乘）与 `SCS/2^k`（除）
- **症状**：FAC 粒度算成 MHz 量级。
- **根因**：原文上标在抽取时丢失（`SCS / 2k`），视觉上像乘。
- **处置**：做量级自检——15 kHz、k=8 应得 **≈58.6 Hz**；若得 3.84 MHz 就是乘错了。
- **校验**：`config.json` 的 `forbidden_patterns` 已把 `SCS×2^` 列为禁忌。

## P6　把"根关系"和"传输域"当成一个维度
- **症状**：写"选定了 Alt1-4，所以 RO 配置已定"。
- **根因**：`Alt1-1..Alt1-4` 与 `TDM/CDM` 是**两个正交维度**（前者=两根是否共轭，后者=是否同 RO），编号风格相似极易混。
- **处置**：在文档里显式画出维度表（维度①根关系 / 维度②传输域 / 维度③配对规则），每条 Agreement 标明它作用于哪个维度。
- **收益**：这一张表往往就是全篇最有信息量的地方。

## P7　同一物理量取错 Set / Case
- **症状**：写 2903.8 而 WA 用的是 2903.6；写 128.28 而 WA 用的是 127.08。
- **根因**：TR 同一张表有 Set1/Set2、case 1/case 2、仰角 a/c/90 多组，数值差在小数位。
- **处置**：取**更保守（更小）**的值，并在溯源表里注明"同表另一组为 X"。
- **校验**：溯源表每行必须写全"表号 + 轨道 + 频段 + 波束直径 + 仰角"四要素。

## P8　位置误差按单程算
- **症状**：20 m 写成 67 ns 而不是 133 ns。
- **根因**：UE 用错误位置算 TA，误差**双程**计入。
- **处置**：定时误差一律 `2Δd/c`；只有"单程延时"这类概念才用 `Δd/c`，且要写清是单程。

## P9　手算步数/位宽
- **症状**：文档写 22299，工具算 22300；位宽结论没变，但读者一复算就失去信任。
- **根因**：浮点除法 + 手工四舍五入。
- **处置**：一律 `skillctl calc`，把输出原样贴进表；并在表下加一行"本表由 `skillctl calc …` 复算"。

## P10　同一条消息里对同一文件连发多个 Edit
- **症状**：多次返回 "Successfully edited"，但后写的覆盖了先写的，内容静默丢失。
- **根因**：每个 Edit 基于读取时的快照。
- **处置**：**改同一个文件必须串行**（一条消息一个 Edit），改完 grep 复核；跨文件批量不受影响。

## P11　表格少一个 `|`
- **症状**：表格某一列整列错位，渲染后数据串行。
- **处置**：`skillctl check` 会逐行比对同表列数并报出行号；含转义竖线 `\|` 的单元格已做处理，不会误报。

## P12　给 WID 未明列的议题借用 A/B/C 编号
- **症状**：把"独立 PRACH 资源"记成 C4/C5，而 WID 的 C4 是移动性流程。
- **根因**：想让映射表"看起来完整"，于是往已有编号上靠。
- **处置**：WID 没明列的，另设 **N1..Nn** 并写派生依据（通常是 WID 的 NOTE 或受影响 TS）；映射表里保留 A/B/C/P 原义。

## P13　只写正增量
- **症状**：增量清单全是"新增/裁决"，读者以为全线推进。
- **根因**：负增量（停滞、未讨论）在素材里"没有内容"，容易被省略。
- **处置**：增量清单强制含"停滞"标签；每场至少列一条负增量，并在小结里点名**结构性缺口**（例：两条并列分支只收口了一条）。

## P14　切块吞掉 FL 分隔行
- **症状**：`blocks.json` 里某块的 `text` 末尾多出 `R1-2607813  FL Summary #2  Moderator (Thales)` 和几行空行。
- **根因**：块的结束点只取「下一个 `Agreement:`」，而 FL 分隔行夹在两者之间。写的时候看不出来（正文是手抄的），
  一旦 `compose` 从 `blocks.json` 注入原文，分隔行就原样进了续篇。
- **处置**：块的结束点 = `min(下一块起点, 下一条 FL 分隔行)`。回归：`blocks.json` 里任何一块的 text 都不该含 `FL Summary`。

## P15　分隔线跟着内容来回搬
- **症状**：`compose` 跑第二遍，凭空多出 6 条 `---`；第三遍再多几条。
- **根因**：解析时 `④ 遗留` 取到小节末尾，把 `---` 也算进内容；重排时又由 `compose` 发一条，越积越多。
- **处置**：**分隔线是结构，不是内容**。解析时从每段首尾剥掉 `^-{3,}$`，由 `compose` 统一在节前发。
  验收标准就一条：同一输入跑两遍，输出字节相同。

## P16　块标题重复 / 行内粗体被抹
- **症状**：14 块生成出 22 个块标题；`TA offset **同时**支持` 变成 `TA offset 同时支持`。
- **根因**：①块的截断点落在「下一块的标签」之前，中间夹着下一块标题行，被当成上一块的内容带走；
  ②清理标题时用了 `replace("**","")`，把行内粗体一起干掉。
- **处置**：①解析时用正则摘掉段尾的 `**AgN｜…**　<sub>…</sub>`；②只剥外层 `**AgN｜` 前缀与收尾 `**`，
  内部粗体保留。回归用例：`compose` 输出的标题数必须等于块数。

## P17　用 blocks.json 覆盖已经排好版的原文
- **症状**：`X = 20 m / X = 50 m / X = 150 m` 退回成 `X= 20m`；`"RO pair"` 变回 `" RO pair "`；行首多出 tab。
- **根因**：docx→txt 抽取会丢表格、丢上标、留 tab。正文里的原文已经人工清理过一轮，`blocks.json` 是原始抽取。
- **处置**：**原文以正文为准**，只有正文里还没有的块才从 `blocks.json` 注入。新注入的原文是朴素文本，
  允许补排版（列表、粗体、上下标），但不许改字——原文字面错误用块后 `〔校〕` 登记，不在原文行里改。

## P18　块标题 `<sub>` 里的 Issue 归属被重建时抹掉
- **症状**：`**Ag11｜SSB-to-RO 映射复用 legacy**　<sub>FL#5 · Issue#2-4</sub>` 重跑一次退化成 `<sub>FL#5</sub>`，
  14 块全部丢掉 `· Issue#x-y`；行数、原文、标题都不变，只有溯源信息没了，`check` 也照样 PASS。
- **根因**：`<sub>` 被当成"由工具生成的结构"。实际上它半结构半内容：`FL#n` 能从 `blocks.json` 的 `fl_round` 算出来，
  `· Issue#x-y` 是 B2 的 flow 判定结果，`blocks.json` 里根本没有。解析时整段丢掉、输出时用算出来的重建，
  就等于把判定成果删了。
- **处置**：**`<sub>` 与块标题一样遵循"正文优先"**。解析时把 sub 原文留下，输出时正文有就用正文的；
  只有新注入的块才回退到 `FL#n`（有 `flow.json` 时再拼上 Issue）。正文的 `FL#n` 与切块算出的不一致时，
  在 stderr 提示「轮次不一致（按正文保留）」，不静默改。
- **回归**：`t_compose_keeps_sub`——同一块跑两遍，`<sub>` 数量不变、Issue 归属还在。

## P19　无标题块 `**AgN**` 被上一块的 raw 吞掉
- **症状**：`**Ag2**　<sub>FL#3</sub>` 在正文里出现两次。块标题总数 = 块数 + 1。
- **根因**：块标题行有两种形态——`**Ag3｜标题**　<sub>…</sub>`（人工写了标题）和 `**Ag2**`（`blocks.json` 里
  没有该块的 `block_title`，工具只发裸标记）。摘标题的正则只认带 `｜` 的那种，裸标记被算进**上一块**的
  raw 段尾，重排时先随上一块输出一次、再由本块输出一次。
- **处置**：按行处理段尾，而不是用一条跨行正则。两种形态都要摘：
  `^\*\*(?:Ag|WA)\d+(?:｜.*)?\*\*(?:[ \t　]*<sub>.*</sub>)?$`。注意 `｜.*` 必须**贪婪**——标题里可能夹行内粗体
  （`… TA offset **同时**支持**`），非贪婪会在第一个 `**` 处停下、匹配失败。块标题识别同理放宽到
  `^\*\*(?:Ag|WA)\d+`，否则 `<sub>` 也跟着丢。
- **回归**：`t_compose_idempotent` 必须用**含块**的正文做夹具——空标签夹具不生成块，永远测不到这一条。
